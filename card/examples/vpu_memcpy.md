# vpu_memcpy.S and vpu_memcpy.c

`vpu_memcpy.S` is generated by `knc-mvex-gen memcpy` and holds a copy
and two clears. The copy is:

```
void *knc_memcpy64(void *dst, const void *src, size_t blocks);
```

It copies whole 64-byte blocks between 64-byte aligned pointers with
`vmovaps`, the full width of the vector unit, unrolled by four so that
four loads issue before the first store needs its result. That unroll is
not a micro-optimisation: the core is in-order with no reorder window, so
overlapping memory latency has to be done in the instruction order itself.

`vpu_memcpy.c` is the harness: it checks every block count from 0 to 64
against `memcpy`, then benchmarks both.

```
cc -O2 -o vpu_memcpy vpu_memcpy.c vpu_memcpy.S
./vpu_memcpy
```

## Why it was written

zstd and xz both spend real time copying bytes, and the card has no byte
or word vector instructions at all (`docs/results/2026-09-20-zstd-vpu.md`),
so moving bytes is the *only* thing the VPU can do for a compressor.
Before that, `cpybench` showed musl's `memcpy` needed about 206 cycles to
move 64 bytes and 72 to move 8: almost all of it size dispatch and
alignment branching on a core that cannot predict a branch. Two
instructions move 64 bytes. The gap looked large.

## Measured 2026-09-20, single thread

| bytes | musl memcpy | knc_memcpy64 | speedup |
| --- | --- | --- | --- |
| 64 | 463.8 MB/s | 755.9 MB/s | 1.63x |
| 128 | 593.9 | 799.0 | 1.35x |
| 256 | 684.8 | 856.1 | 1.25x |
| 512 | 743.4 | 860.2 | 1.16x |
| 4096 | 806.6 | 897.0 | 1.11x |
| 65536 | 815.4 | 903.5 | 1.11x |
| 1 MiB | 816.5 | 909.7 | 1.11x |

Correct on all 65 block counts tested.

The shape of that curve is the result. The win is 1.63x at 64 bytes, where
the scalar version is paying its fixed overhead, and collapses to 1.11x by
4 KiB, where both are simply waiting on memory. A single-threaded copy at
909 MB/s moves 1.8 GB/s in total, which is already about what one thread
can pull (`card/examples/membw.md`: 54.4 GB/s across 57 threads, so
roughly 950 MB/s each). **The copy path is bandwidth-bound per thread, not
instruction-bound**, so the vector unit has almost nothing left to win once
the fixed overhead is gone.

## Limits of this version

Both pointers must be 64-byte aligned and the length a multiple of 64.
KNC has no unaligned vector load: it needs a `vloadunpackld`/`hd` pair,
which the encoder does not emit yet. That matters, because compressor
copies are almost never aligned, and it is the reason this was not carried
into zstd (`docs/results/2026-09-20-zstd-vpu.md`).

Adding the unpack pair to `knc-mvex` is the obvious extension. It would
make this a drop-in `memcpy` for the card, which is worth doing for its own
sake even though it will not rescue a compressor: every program on the card
goes through musl's scalar version today.

## The clear kernels, and a benchmark that lied

`knc-mvex-gen memcpy` also emits two clears:

```
void *knc_memset64(void *dst, size_t blocks);      /* vmovnrngoaps */
void *knc_memset64_ord(void *dst, size_t blocks);  /* vmovaps      */
```

They exist because FSST12 in FastLanes zeroes a 24 MB counter structure
four times per symbol table build, and on the card that clear was half
the cost of compressing a real file.

**The first measurement of it was wrong and said the opposite.** It timed
five back-to-back `memset(p, 0, SZ)` calls on a buffer nothing read
afterwards, so the compiler deleted four of them, and the apparent
4.82 GB/s was mostly nothing happening. The conclusion drawn from it,
that a scalar clear already saturates the memory system and a wider store
could not help, was false. The rewrite puts every kernel behind a
function pointer in a thread, checks each one zeroes all 25174016 bytes
of a buffer pre-filled with `0xa5` before timing anything, and gets:

| threads | musl `memset` | `vmovaps` | `vmovnrngoaps` |
| --- | --- | --- | --- |
| 1 | 0.90 GB/s | 1.72 GB/s | **4.93 GB/s** |
| 4 | 3.70 | 6.90 | 17.84 |
| 16 | 13.41 | 21.47 | 45.62 |
| 64 | 22.75 | 38.89 | **77.79** |

Two separate effects, and the split matters. Going from 8-byte stores to
64-byte stores is worth about 1.9x: the scalar clear is issue-limited on
an in-order core, not bandwidth-limited. Not reading the line before
overwriting it is worth another 2.9x on top, because a normal store
misses, fetches 64 bytes it is about to discard, and then writes them
back. `vmovnrngoaps` tells the cache to skip the fetch (ISA reference
327364-001 page 396).

`vmovnrngoaps` is weakly ordered. The kernel ends with
`lock addq $0, (%rsp)`, the fence the reference recommends over `cpuid`,
so callers need no fence of their own.

**The general lesson for this card:** a microbenchmark of a memory
primitive has to defeat dead-store elimination and has to check its own
output, or it measures the optimiser. Both kernels are checked byte by
byte against musl before any timer starts.
