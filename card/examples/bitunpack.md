# bitunpack.c and bitunpack.S

The measurement that decides whether hand-written MVEX is worth pointing at
compression on this card. `bitunpack.S` is generated by
`knc-mvex-gen bitunpack` and holds `knc_unpack_b5`, `knc_unpack_b11` and
`knc_unpack_b16`: unpack 1024 values of N bits into 1024 `int32`.

```sh
phi put card/examples/bitunpack.c /tmp/bitunpack.c
phi put card/examples/bitunpack.S /tmp/bitunpack.S
phi run sh -c 'cd /tmp && cc -O2 -o bitunpack bitunpack.c bitunpack.S && ./bitunpack'
```

## The layout

Bit-packing is not vectorisable in its ordinary form: value `i` sits at bit
`N*i` of one contiguous stream, so extracting sixteen consecutive values
needs sixteen different shift counts. The fix, which is what FastLanes is
for, is to change the layout rather than the arithmetic.

Value `i` of a block goes to **lane `i % 16` at position `i / 16`**. Each
of the sixteen lanes then carries its own independent 64-value bitstream,
and because every lane is at the same position at the same time, every
lane is at the same bit offset. Word `w` of all sixteen lanes is one
64-byte vector at `packed + 64*w`, and one shift-and-mask pair extracts one
value from all sixteen lanes at once.

Nothing crosses a lane. That is the property that matters here: the card
has no byte shuffle and no cheap cross-lane permute, so a layout needing
either would be dead on arrival (`docs/research/compression-on-knc.md`).

Four fixed sequences per value, chosen when the code is generated because
the bit offsets are compile-time constants:

| Case | Instructions |
| --- | --- |
| starts at a word boundary | `vpandd` |
| ends at a word boundary | `vpsrld` |
| inside one word | `vpsrld`, `vpandd` |
| straddles two words | `vpsrld`, `vpslld`, `vpord`, `vpandd` |

No branch, no variable shift, no table lookup.

## Scheduling is most of the performance

The first version emitted one value's whole chain before starting the
next. It ran at 1.07 values per cycle: about fifteen cycles for a
four-instruction chain, which is what an in-order core does when every
instruction waits on the one before it.

The generator now emits phase by phase across a group of eight values: all
the first shifts, then all the second shifts, then all the ors, then all
the masks, then all the stores. Consecutive instructions are then never
dependent. Same instruction count, 1.8x the throughput.

## Results, 2026-09-20, one thread

Three implementations of the same unpack. `stream` is the ordinary way a
codec does it, scalar over a contiguous bitstream, which is the baseline
that matters because it is what the card runs today. `lanes` is scalar
over the interleaved layout, which isolates how much comes from the layout
rather than the vector unit. `vpu` is `knc_unpack_bN`.

| bits | pass | stream M/s | lanes M/s | vpu M/s | vs stream | vs lanes |
| --- | --- | --- | --- | --- | --- | --- |
| 5 | hot | 47.8 | 26.1 | **2257.1** | 47.3x | 86.6x |
| 5 | streaming | 41.9 | 24.6 | 360.2 | 8.6x | 14.6x |
| 11 | hot | 42.8 | 24.5 | **1970.9** | 46.0x | 80.4x |
| 11 | streaming | 38.7 | 23.1 | 312.8 | 8.1x | 13.6x |
| 16 | hot | 51.7 | 27.2 | **2985.1** | 57.7x | 109.8x |
| 16 | streaming | 45.1 | 25.2 | 294.5 | 6.5x | 11.7x |

`hot` repeats one block in L1 and measures instructions; `streaming` walks
16 MiB of output and measures memory. Correctness is checked first: all
three implementations against the original values, every block.

Three readings.

**The vector unit is worth 46 to 58 times the scalar code when the data is
in cache.** This is the first workload in the project where the card's
vector unit produces that kind of margin, and the reason is structural:
sixteen 32-bit lanes, three or four instructions per sixteen values, no
control flow, no cross-lane movement.

**The layout alone is a loss, not a win.** `lanes` is consistently *slower*
than `stream` in scalar, 24 to 27 M/s against 42 to 52. The interleaved
layout costs scalar code a multiply and a strided access per value and buys
it nothing; it only pays when something can read sixteen lanes at once.
FastLanes reports the opposite on modern hardware, where the compiler
auto-vectorises the scalar form. Nothing auto-vectorises to MVEX here, so
on this card the layout is strictly a vector-unit enabler.

**Streaming is bandwidth-bound, at 6.5 to 8.6x.** 312 M values per second
at 11 bits is 1.25 GB/s written plus 0.43 GB/s read, and one thread reaches
about 950 MB/s of read bandwidth (`membw.md`). The hot-to-streaming drop of
6x is memory, not instructions, which means the streaming number is the one
that should scale with threads: the card reaches 80.5 GB/s at 114 threads
against 35.7 on the host.

## What is not measured here

Threads. Every number above is one thread of 228. The single-thread issue
rate is also a ceiling: KNC needs at least two threads per core to fill the
pipeline, so 1.79 values per cycle at 11 bits is close to what one thread
can do, not what one core can do.

The host. There is no host-side comparison yet, so this says the card beats
*itself*, not that it beats the machine it is plugged into. That comparison
needs an AVX2 implementation of the same layout and is the next honest
step.

Widths 5, 11 and 16 only. 11 is the awkward general case (values straddle
words), 5 is narrow, 16 never straddles anything. The generator is
parameterised by width, so the remaining widths are one line; they are not
generated yet because three were enough to answer the question.
