# libknc: the card's vector unit as a library

`knc.h`, `knc.hpp` and `libknc.a`. Everything behind them is hand-encoded
MVEX generated by `host/crates/knc-mvex`, because no compiler in this stack
(or anywhere) emits Knights Corner vector instructions. There is no C and
no Rust inside the library: it is one generated assembly file, two headers,
and a dispatch table.

```sh
card/lib/knc/build.sh                       # generate, assemble, install
knc-cc -O2 prog.c -lknc                     # on the host, for the card
cc -O2 prog.c -lknc                         # on the card itself
c++ -std=c++17 -O2 prog.cpp -lknc           # C++, through knc.hpp
```

## What it provides

| Symbol | What |
| --- | --- |
| `knc_unpack(out, packed, bits)` | one block of 1024 values of `bits` bits into 1024 `int32` |
| `knc_pack(packed, values, bits)` | the inverse |
| `knc_unpack_table[33]`, `knc_pack_table[33]` | the per-width kernels, to hoist the dispatch out of a loop |
| `knc_memcpy64(dst, src, blocks)` | 64-byte aligned block copy |
| `knc::codec`, `knc::aligned_buffer` | the C++ layer in `knc.hpp` |

Widths 1 to 32, both directions, 64 kernels. All pointers must be 64-byte
aligned. A width outside 1 to 32 returns without touching memory: the
dispatch is a computed jump and this library is called from Python and
JavaScript, where the width can come from data. `knc.hpp` throws instead.

## The layout is not a bitstream

This is the one thing a caller has to understand. Ordinary bit-packing puts
value `i` at bit `N*i` of a contiguous stream, so sixteen consecutive values
need sixteen different shift counts and nothing vectorises.

Here, **value `i` lives in lane `i % 16` at position `i / 16`**. Each of the
sixteen lanes carries its own 64-value stream and all sixteen sit at the
same bit offset at once, so word `w` of every lane is a single 64-byte
vector at `packed + 64*w` and one shift-and-mask pair extracts one value
from all sixteen. Nothing crosses a lane, which matters because the card
has no byte shuffle and no cheap cross-lane permute
(`docs/research/compression-on-knc.md`).

This is the FastLanes unified layout at a 512-bit register width. Packed
bytes produced here are **not** interchangeable with an ordinary packed
bitstream, and `knc_test.c` checks them against an independent scalar model
of the layout rather than only round-tripping.

## Why there is no C or Rust in it

`CONTRIBUTING.md` says Rust first, C only where Rust is not an option. The
library is neither: it is generated assembly, because the instructions have
no compiler. What would otherwise be a C or Rust shim, the width dispatch,
is two tail-calling thunks the generator emits alongside the kernels, so
`libknc.a` pulls in no runtime of any kind and cannot collide with musl,
libc++, CPython or QuickJS when it is linked into them.

`knc.h` and `knc.hpp` are hand-written because a C ABI needs a C header.
`card/lib/knc-rs` is the Rust view of the same library.

## Files

| File | What |
| --- | --- |
| `build.sh` | generates the kernels, assembles, audits, installs into the sysroot and packages for `/opt/phi` |
| `knc.h` | the C ABI |
| `knc.hpp` | C++17 layer: `knc::codec`, `knc::aligned_buffer`, range-checked entry points |
| `knc_test.c` | conformance for all 64 kernels, on the card |
| `knc_bench.cpp` | throughput at every width, across threads; also the C++ layer's smoke test |
| `lanes_bench.cpp` | the scalar baselines alone, so the same source runs on the host and the card |

`knc_bench.cpp` and `lanes_bench.cpp` are C++ rather than Rust deliberately:
`lanes_bench.cpp` has to be compiled by the *host's* optimiser with full
AVX2 to measure what FastLanes' auto-vectorisation actually achieves there,
and the two files must be the same language to be comparable.

## Measured, 2026-09-20, 11 bits

Decode, millions of values per second. `stream` is a contiguous bitstream
scalar, `lanes` is scalar over this layout, `libknc` is the vector kernels.

| Machine | Threads | stream | lanes | libknc |
| --- | --- | --- | --- | --- |
| card | 1 | 37.8 | 92.6 | **403.9** |
| card | 228 | 3396 | 6355 | **12556** |
| host | 1 | 1596.5 | **3913.8** | n/a |
| host | 16 | 10071 | **30836** | n/a |

The host's `lanes` column is FastLanes working as designed: the same scalar
source, auto-vectorised to AVX2 by the compiler. The card's `libknc` column
is the same job done by hand because the compiler cannot.

Three things follow.

**libknc saturates the card's memory.** 12556 M values per second at 11
bits is 4 bytes out and 1.375 in per value, about 67 GB/s, against the 66.0
GB/s that `card/examples/membw.md` measures at 228 threads. There is no
throughput left to find; the kernels are done until the data moves less.

**The card reaches 0.41 of the host on this workload.** That is the best
ratio in this project: xz managed 0.22 to 0.26, zstd 0.03 to 0.07, scalar
integer work 0.14. It is still a loss, and it is a loss against sixteen
threads with sixteen fewer cores.

**The vector unit is what closes it.** Card scalar against host scalar on
the same layout is 6355 against 30836, or 0.21x. libknc takes that to
0.41x. Per thread the vector unit is worth 4.4x over the card's own best
scalar code, and 10.7x over how a codec would ordinarily do it.

## Building it

`build.sh` needs the musl sysroot and `make build` for the audit tool. It
installs `libknc.a` and both headers into `toolchain/build/sysroot/usr`,
and writes `phi-libknc.tar.gz` for the card, whose clang searches
`/opt/phi/usr`:

```sh
phi put ~/.cache/intel-phi-3120a-build/userland/libknc/phi-libknc.tar.gz /tmp/libknc.tar.gz
phi run sh -c 'tar -xzf /tmp/libknc.tar.gz -C /'
```

The audit must come back clean. It did not the first time: `phi-isa-audit`
gave the `72 /digit ib` shifts no immediate byte, lost sync, and reported
177 illegal instructions that were not there. That was a real bug in the
audit tool, fixed in the same change as this library.
