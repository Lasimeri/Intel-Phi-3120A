# 2026-09-17: phitop, the card's resources live from the host

The remote resource viewer (`host/crates/phitop`, ADR 0009): every
interval the host asks the card's agent for a sample (`Stat`, answered
from /proc and sysfs even while a command runs) and the daemon for its
PCIe byte counters (`Traffic`), and draws every hardware thread's load
on a 57 by 4 grid, the die temperatures, memory and swap, PCIe rates by
path and direction, the card's disk and network rates, and its
processes. Nothing new runs on the card beyond the agent it already had.

## A frame under load

Mandelbrot render (maxiter 4000, 228 threads) and held the card's rpc
session for the whole 17 s; the sample went through as a sideband:

- The render took 17.18 s at 1.70 Giter/s, the same as on 2026-09-15
  without a viewer sampling it: the sideband costs nothing measurable.
- The agent's own sampling shows as 2.9 percent of one hardware thread
  at a 3 s interval. The first version read all 1500 kernel threads'
  stat files every second and showed 16.7 percent, so the agent now
  re-reads known kernel threads every fourth sample and sends only the
  ones whose CPU time moved (`card/agent/src/stat.md`).
- Resident sizes come from `/proc/[pid]/status`: the `rss` field of
  `/proc/[pid]/stat` reads 0 for every small process on this card. It
  reports the global part of a per-CPU counter whose batch is 456 pages
  with 228 CPUs (`percpu_counter_batch`, mm/memory.c `get_mm_counter`),
  so a process under 1.8 MiB per CPU never flushes into it; `status`
  sums the parts.
- Die temperatures rose from 52 to 58 C over the render (the SBOX's
  recorded maximum, 66 C, dates from an earlier session).

## PCIe rates against the card's own counters

A 1.5 GiB write to `/data` (`dd bs=1M conv=fsync`, 166 MB/s over the
whole run with the fsync) seen in two 2 s windows:

```
pcie  to card 1.1 MB/s (dma 1.1 MB/s, aperture 10.6 kB/s)   from card 377.2 MB/s (dma 377.2 MB/s, aperture 78.1 kB/s)
card   phiblk0 read 0 B/s write 377.2 MB/s   phiblk1 read 0 B/s write 0 B/s         phi0 rx 0 B/s tx 0 B/s
pcie  to card 5.8 kB/s (dma 0 B/s, aperture 5.8 kB/s)   from card 189.9 MB/s (dma 189.8 MB/s, aperture 51.2 kB/s)
card   phiblk0 read 0 B/s write 187.8 MB/s   phiblk1 read 0 B/s write 0 B/s         phi0 rx 0 B/s tx 0 B/s
```

The `pcie` line is the host's DMA completion counter, the `card` line
is the card's `/proc/diskstats`: two independent counters, sampled over
the same window, agree to within the sampling skew. The aperture share
(tens of kB/s) is the ring traffic: block requests and completions, the
rpc frames of the sample itself, the console.

Reading the file back with `iflag=direct` ran at 55 MB/s in one window
and 185 MB/s for a fresh 256 MiB file (direct 1 MiB reads become two
512 KiB requests of up to 64 page-sized records each: one DMA
completion per 4 KiB page, against one per 512 KiB for a buffered
read). Buffered reads were 846 MB/s on 2026-09-16.

## Open item: a direct read stalled once

During the first run of the write test above, the read back of the
1.5 GiB file with `iflag=direct` (bs=1M, through a `phictl exec`
session with `| tail -1`) ran at 55 MB/s for one window and then
stopped: `dd` sat in state D at 0 percent, `phiblk0` showed no traffic,
the daemon's threads were all asleep in nanosleep (nothing to serve),
no anomaly was logged by the disk service and no warning by the
driver (unknown tag, idle tag, inconsistent indices all silent), and a
later `phictl exec` waited behind the stuck session. The block layer
never times the request out because the driver has no `timeout`
operation, so the state was permanent until a restart, which found the
ext4 journal intact (`recovery complete`).

Two attempts to reproduce it over SSH (256 MiB and 1.5 GiB, the second
sampled by phitop every 2 s) completed at 185 and 386 MB/s with
`inflight` back at 0 0. What to capture next time it happens:
`/sys/block/phiblk0/inflight`, the stuck process's `/proc/PID/stack`,
and the block channel's ring indices from the host. The viewer itself
stayed live through the stall: the `Stat` sideband does not need the
session, which is the reason it exists.


## What the viewer does not show

Power (the SMC holds it; not requested by this port) and the board
sensors (same), so the temperature line says so. PCIe rates are what
this daemon moved, counted at its two copy paths; the link's own
counters are not read.
