# 2026-09-19: xz 5.8.3 on the card, and what LZMA costs here

Question asked: what compression throughput can the card reach, and how
does it compare with the host running the same code.

Host 7.2.6-1-cachyos, Ryzen 7 5800X, 16 threads, xz 5.8.3 from Arch. Card
running xz 5.8.3 built by `card/userland/components/xz.sh` with the same
source, same version, 0 illegal instructions.

Corpus: 473 MiB `tar` of the Linux 7.2.3 tree (`arch drivers/net
drivers/gpu/drm/i915 kernel lib mm fs include sound`), built with
`--sort=name --owner=0 --group=0 --numeric-owner --mtime=2026-01-01` so it
is byte-identical on both machines, and transferred to the card with
`phi put` at 10.8 MB/s.

## Readings

**The card is about a quarter of the host, at best.** 78 against 296 MB/s
at `-1` (0.26x), 10.7 against 47.6 at `-6` (0.22x). That is better than the
card's pure integer ratio of 0.14x (`2026-09-15-pi-bbp.md`) and far short
of its 2.25x memory-bandwidth advantage (`card/examples/membw.md`). The
reason is not established: the hardware counters that would settle it do
not work on this part (see the retraction below).

**Tuning is worth 7x, and the defaults are terrible.** At `-6` the card
goes from 1.5 MB/s to 10.7 MB/s purely by changing thread count and block
size. Nothing about the data or the algorithm changed. The default block
size at `-6` is 3x the 8 MiB dictionary, so a 473 MiB input makes only 19
blocks and *at most 19 of 228 threads can ever run*. Block count, not
thread count, is the real parallelism limit in xz, and on a 228-thread
machine that bites immediately.

**Usable thread count is set by RAM divided by dictionary size.** The first
version of this record blamed L2 port contention at four threads per core,
citing `-T228` with 2 MiB blocks (4.3 MB/s) losing to `-T114` with 4 MiB
blocks (10.7 MB/s). That comparison was confounded: it varied thread count
and block size together. Repeated with block size held at 4 MiB on a
945 MiB corpus (236 blocks, so every thread has work):

| Threads | Time | Throughput |
| --- | --- | --- |
| 57 | 76 s | 12 MB/s |
| 114 | 89 s | 10 MB/s |
| 171 | 166 s | 5 MB/s |
| 228 | 207 s | 4 MB/s, **OOM-killed** |

Monotonically worse, and the last run was killed by the kernel. The cause
is memory **capacity**, not bandwidth and not port contention. liblzma
allocates roughly 11.5 times the dictionary per encoder thread, and
`--block-size` does not change that: preset `-6` keeps its 8 MiB dictionary
whatever the block size, so shrinking blocks lets more threads engage
without making any of them cheaper.

    -6   8 MiB dict    ~94 MiB/thread    5669 MiB RAM /  94 =  ~57 threads
    -1   1 MiB dict    ~12 MiB/thread    5669 MiB RAM /  12 = ~450 threads
    -9  64 MiB dict   ~700 MiB/thread    5669 MiB RAM / 700 =   ~8 threads

That predicts what the `-1` sweep actually did: 228 threads was the *best*
configuration there (78 MB/s, beating 114 at 67), because at a 1 MiB
dictionary all 228 fit in RAM with room to spare. There is no
four-threads-per-core penalty in this workload. The bandwidth measurement's
turnover at two threads per core (`card/examples/membw.md`) is real but
does not apply here: xz is issue-bound, not bandwidth-bound.

**Practical rule for this card: use `-1 -T228`, not `-6`.** The highest
throughput measured, 78 MB/s, came from the preset with the smallest
dictionary and every thread engaged.

## Where the time goes: retracted

An earlier version of this record claimed, from `phiperf`, that xz on the
card runs at 1.445 instructions per cycle with a 67.5% branch
misprediction rate, and concluded it was issue-bound rather than
stall-bound. **That was wrong and is withdrawn.** The counters it rested on
do not work on this part.

What the PMU actually does, measured on 2026-09-19 with `xz -6 -T1` over
8 MB, two events only so nothing multiplexes:

```
$ phiperf -n -r 0x2a,0x16 xz -6 -T1 -c /tmp/p8
raw 0x2a (cycles)         27557970377       100%
raw 0x16 (instructions)             0       100%
wall                           25.099 s
```

Cycles is right: 27.56e9 at 1.1 GHz is 25.05 s against a 25.10 s wall.
Instructions reads **zero**. With the default six events on a two-counter
PMU everything multiplexes at 33%, and the scaled instruction count came
back as 15e9 in one run and 993,910 in another for comparable work, four
orders of magnitude apart. Any ratio built on that number, including the
IPC figure above, is meaningless.

`0x0016` is what `arch/x86/events/intel/knc.c` maps
`PERF_COUNT_HW_INSTRUCTIONS` to, so this is not a wrong event code in
`phiperf`; the counter itself does not appear to work here. Until that is
understood, **only cycles should be trusted on this card**, and only
without multiplexing. `card/examples/phiperf.md` carries the caveat.

What survives, because it rests on wall-clock rather than counters:

- Swapping the match finder from the binary tree `bt4` to the hash chain
  `hc4`, which does far less work, changed nothing (20 s against 21 s),
  though `bt4` compressed better. On the host `bt4` is 2 to 3 times slower
  than `hc4`. The match finder is therefore not the bottleneck here.
- Enabling liblzma's branchless C decoder paths made no measurable
  difference, which is consistent with decompression (236 MB/s) being far
  from the limit either way.

Why the card is slow at this is therefore **not established**. The missing
CMOV remains the plausible explanation, since LZMA's inner loop is a
data-dependent select and upstream ships branchless assembly for exactly
that reason on x86-64, but it is a hypothesis and this record no longer
claims otherwise.

Enabling liblzma's own branchless C decoder paths
(`LZMA_RANGE_DECODER_CONFIG=0x0F` instead of `0`, mask arithmetic rather
than CMOV, still 0 illegal instructions) made no measurable difference to
decompression, which runs at 236 MB/s and is nowhere near the bottleneck.
The build keeps `0x0F` anyway, since it is the path every non-x86 target
uses and it costs nothing.

**Compression ratio is identical.** 13% on both machines at both presets,
so this is purely a speed comparison; the card produces the same output.

## Verdict

Not worth offloading. The host does the same job four times faster and
needs no tuning to do it. What the measurement is good for is calibration:
xz is a realistic branchy integer workload with an unpredictable inner
loop, and the card lands at 0.22 to 0.26x on it, between its 0.14x on pure
integer work and its 2.25x on pure bandwidth.

## A portability bug found on the way

`src/liblzma/rangecoder/range_decoder.h` enables hand-written x86-64 inline
assembly whenever `__x86_64__` is defined:

```c
#ifndef LZMA_RANGE_DECODER_CONFIG
#	if defined(__x86_64__) && !defined(__ILP32__) ...
#		define LZMA_RANGE_DECODER_CONFIG 0x1F0
```

It uses `__x86_64__` as a proxy for "has CMOV". The card is x86-64 without
CMOV, so the assembly compiles in and no compiler flag can remove it:
`phi-isa-audit` found 216 `cmov` instructions, all in `lzma_decoder.o`.
`-DLZMA_RANGE_DECODER_CONFIG=0x0F` selects the portable branchless C
path that every non-x86 target already uses (bits 0x01 to 0x08 are mask
arithmetic, 0x1F0 is the assembly). This is the class of assumption the card is
good at exposing, and it is the same reason `docs/plan.md` lists the card
as a differential-testing partner.

Two build traps are recorded in `xz.md`: `--disable-shared` governs only
liblzma and leaves the driver dynamic (the card has no loader, so it fails
with a bare "not found"), and libtool filters `-static` out of the program
link, so the script verifies the result and relinks by hand.
