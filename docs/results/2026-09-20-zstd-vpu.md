# 2026-09-20: porting zstd to the VPU, and why it stops at memcpy

Asked: port zstd to use the vector unit. Answer: the hot paths cannot use
it, the one path that can is already bandwidth-bound, and the measured
ceiling on the whole idea is a few percent. A working VPU block copy came
out of the attempt and is kept (`card/examples/vpu_memcpy.md`).

## The constraint that decides it

Knights Corner has **no byte or word integer vector instructions at all.**
Extracted from the ISA reference (327364-001) and counted:

```
$ grep -icE 'vp(add|sub|cmpeq|min|max)[bw]\b|pshufb|vpsadbw' isa.txt
0
```

Every integer vector instruction ends in `D` (32-bit lanes) or `Q`
(64-bit): `VPADDD`, `VPSUBD`, `VPCMPEQD`, `VPCMPD`, `VPCMPUD`, `VPSLLD`,
`VPSRLVD`, `VPANDD`, `VPORQ`, `VPXORD`, `VPSHUFD`. There is no
`vpcmpeqb`, no `pshufb`, no `vpsadbw`. Unaligned vector access needs a
`vloadunpackld`/`hd` pair rather than a single instruction.

Compression is byte-oriented. Every standard SIMD technique in a
compressor (byte-wise match comparison, byte shuffles for literal
handling, saturating byte arithmetic) is unavailable here, not merely
slow. The only vectorisable operation left is moving bytes, which is
lane-agnostic.

## What that leaves, and what it is worth

zstd's hot paths at level 1, in rough order of cost:

| Path | Vectorisable on KNC? |
| --- | --- |
| Hash lookup and insert | No. Random access; `vgatherd`/`vscatterd` exist but serialise internally |
| `ZSTD_count` match length | Only at 32-bit granularity with a scalar tail, and matches are short |
| `ZSTD_wildcopy`, literal copy | **Yes**, this is the one |
| FSE/Huffman entropy coding | Serial bitstream; the lane-interleaved rewrite is a different program |

So: the copy path, and nothing else.

## Measuring the copy path first

`cpybench` on musl's `memcpy`, single thread:

| bytes | ns/call | cycles at 1.1 GHz |
| --- | --- | --- |
| 8 | 65.3 | ~72 |
| 16 | 89.0 | ~98 |
| 64 | 187.1 | ~206 |
| 65536 | 131862 | 497 MB/s, bandwidth-bound |

206 cycles to move 64 bytes is overhead, not bandwidth: size dispatch and
alignment branching on a core that cannot predict a branch. Two vector
instructions move 64 bytes. That looked like a large gap, so the kernel
was written.

## The kernel, and the result

`knc-mvex-gen memcpy` now emits `knc_memcpy64`: `vmovaps` load and store
unrolled by four, so four loads issue before the first store needs its
result. Correct on all 65 block counts tested against `memcpy`.

| bytes | musl | knc_memcpy64 | speedup |
| --- | --- | --- | --- |
| 64 | 463.8 MB/s | 755.9 MB/s | **1.63x** |
| 256 | 684.8 | 856.1 | 1.25x |
| 4096 | 806.6 | 897.0 | 1.11x |
| 1 MiB | 816.5 | 909.7 | **1.11x** |

The curve is the answer. 1.63x at 64 bytes is the fixed overhead being
removed. By 4 KiB it is 1.11x, because both versions are waiting on
memory: 909 MB/s of copy is 1.8 GB/s of traffic, and one thread can pull
roughly 950 MB/s (`card/examples/membw.md`). **The copy path is
bandwidth-bound per thread.** Once the scalar overhead is gone the vector
unit has almost nothing left to win.

## Why it was not carried into zstd

Three reasons, in order of how badly each one hurts:

1. **The ceiling is too low.** Copies are a fraction of zstd's time; a
   1.1x to 1.6x improvement on that fraction is a few percent end to end.
   zstd on the card runs at 0.03 to 0.07x the host
   (`2026-09-19-zstd.md`). A few percent does not change that.
2. **The alignment does not fit.** `knc_memcpy64` needs both pointers
   64-byte aligned. Compressor copies are at arbitrary offsets by
   construction: a match is wherever the match is. Supporting that needs
   the `vloadunpack` pair in the encoder, which is real work for a win
   already known to be small.
3. **The copies are short.** zstd level 1 matches are typically single
   digits to low tens of bytes, and `wildcopy` rounds to 8 or 16 byte
   granules. The 1.63x measured at 64 bytes is the *best* case; at 16
   bytes a 64-byte-wide instruction is mostly waste.

## What is kept

`knc_memcpy64` and its harness, because they are correct, measured, and
the second hand-written vector kernel in the project after the Mandelbrot
work. The obvious next step, independent of compression, is adding
`vloadunpackld`/`hd` to `knc-mvex` and making this a general `memcpy` for
the card: every program there uses musl's scalar version today, and the
1.63x at small sizes applies to all of them.

## The general rule, restated

`2026-09-19-zstd.md` found that the card closes the gap on algorithms that
are expensive per byte and loses on cheap ones. This adds the vector
dimension: **the VPU helps only where work is wide, regular and at least
32 bits per lane.** Compression is none of those. The Mandelbrot kernel
gets 1.47x over the host's AVX2 because it is float64 arithmetic in eight
independent lanes; a compressor is byte-serial with data-dependent control
flow, which is the opposite of what this unit was built for.
