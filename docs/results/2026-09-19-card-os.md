# The card as an ordinary Linux system: FHS, persistent /etc and /var, 6 GiB of swap, clean shutdown, and a host reboot that needs nobody

Host kernel 7.2.6-1-cachyos, card kernel 7.2.3 plus the 28-patch series
(`7.2.3-00028-gca98169c13d4`), initramfs rebuilt from
`card/initramfs/build.sh`. Card booted by the `phi.service` user unit with
`--disk /mnt/1TB-NVMe/phi/disk.img --host-mem 6G --forward 2222:22`.

## 1. Host memory as swap, 6 GiB

`--host-mem 6G` replaces the 4G the unit carried since 2026-09-16.

```
$ phi run sh -c 'cat /proc/swaps; free -m | tail -1'
Filename        Type       Size     Used  Priority
/dev/phiblk1    partition  6291452  0     -1
Swap:           6144        0       6144
$ phi run blockdev --getsize64 /dev/phiblk1
6442450944
```

`/dev/phihost`, the same window mapped for direct access, is still present
and readable, so widening the block device did not cost the shared mapping.

### Under pressure

The first attempt filled `/tmp` and proved nothing: `/tmp` is a tmpfs,
capped at half of RAM, so `dd` stopped at 2.8 GB with the swap untouched.
`card/examples/memhog.c` allocates anonymous memory instead, one store per
4 KiB page, and reads it all back against a per-page value.

```
$ phi run /tmp/memhog 8192 --verify
allocating 8192 MiB in 32 chunks of 256 MiB
  touched 5120 MiB (10.4 s)
  touched 6144 MiB (17.3 s)
  touched 8192 MiB (29.7 s)
touch:  8192 MiB in 29.74 s (289 MB/s)
verify: 8192 MiB in 74.94 s (115 MB/s), 0 mismatches
```

8192 MiB allocated and verified on a card with 5669 MiB of usable GDDR5:
about 2.5 GiB lived in host RAM and came back byte-correct. The touch rate
holds near 490 MB/s while pages are resident and drops to about 170 MB/s
once eviction starts, which is the ring's block path doing the writing.

`memhog` was compiled **on the card** with the native clang in `/opt/phi`,
which is also a check that the persistent toolchain survived the reboots
below.

## 2. Filesystem layout

The image now carries an FHS tree (`/usr/{bin,sbin,lib}`, `/var`, `/run`,
`/srv`, `/mnt`, `/media`, `/opt`) and an `/etc` skeleton at
`/lib/phi/etc-skel`. `init` binds five directories from the disk:

```
$ phi run grep phiblk0 /proc/mounts
/dev/phiblk0 /data    ext4 rw,noatime 0 0
/dev/phiblk0 /etc     ext4 rw,noatime 0 0
/dev/phiblk0 /var     ext4 rw,noatime 0 0
/dev/phiblk0 /opt/phi ext4 rw,noatime 0 0
/dev/phiblk0 /root    ext4 rw,noatime 0 0
/dev/phiblk0 /home    ext4 rw,noatime 0 0
```

`/etc` holds `TZ dropbear/ fstab group hostname hosts mtab os-release passwd
profile resolv.conf shells`. `passwd`, `group`, `shells`, `os-release` and
the dropbear host keys are copied from the skeleton on every boot, so a
rebuilt image stays authoritative for who may log in; `hostname`, `hosts`,
`profile`, `fstab`, `TZ` and `resolv.conf` are seeded only when absent.

Persistence test: `hostname` set to `phi-test` and a line appended to
`/etc/profile`, then a full stop and start of the unit. Both survived. The
login shell reads the profile:

```
$ phi sh 'echo $PATH'
/opt/phi/bin:/bin:/sbin:/usr/bin:/usr/sbin
```

`/var/log/messages` accumulated one `syslogd started` line per boot across
three boots, so the log is persistent rather than reset.

## 3. Clean shutdown, and the three bugs in the way

The goal: a stop that leaves the filesystem clean, so the next mount does
not replay the journal. Getting there took three fixes, each found by
measurement.

**`poweroff -f` never reached init.** `phi-down.sh` and the unit's
`ExecStop` both sent `poweroff -f`, which calls `reboot(2)` from the calling
shell and never signals PID 1. The shutdown handler in `init` existed and
had never run. Both now send plain `poweroff`, which busybox delivers to
PID 1 as SIGUSR2.

**The host stopped serving the disk mid-unmount.** The handler killed
`phi-agent` in its first `killall`. The host's stop sequence waits for the
agent to stop answering and then ends `phictl`, so the block channel went
away while the superblock write was still in flight: `dumpe2fs` showed a
`Last write time` from the *previous* boot. The agent is now stopped last,
after the unmount, so "the agent stopped answering" means "init is done".

**`killall syslogd` matched nothing.** `init` started it as
`busybox syslogd`, so the process's `comm` is `busybox` and `killall
syslogd` does not match. syslogd kept `/var/log/messages` open, which made
`mount -o remount,ro /data` fail with EBUSY:

```
$ phi run sh -c 'busybox fuser -m /data'
1533
$ phi run sh -c 'tr "\0" " " < /proc/1533/cmdline; readlink /proc/1533/fd/3'
/bin/busybox syslogd -O /var/log/messages -s 2048 -b 4
/var/log/messages
```

syslogd and klogd are now started through their applet symlinks
(`/bin/syslogd`, `/bin/klogd`), which gives them the right `comm`.

The handler also detaches the five bind mounts with `umount -l` before
touching `/data`, because the console shell's working directory is normally
`/root`, a bind of the same filesystem; a plain `umount` of it fails and
leaves the superblock mounted, and therefore dirty, while still reporting
success for `/data` itself.

### Result

Before, every boot:

```
EXT4-fs (phiblk0): recovery complete
```

and `dumpe2fs -h` listed `needs_recovery` and `orphan_present` among the
features. After, three consecutive stop and start cycles:

```
cycle 1: clean and unmounted
cycle 2: clean and unmounted
cycle 3: clean and unmounted
```

with no `recovery complete` line on any of the three mounts, and the
features line no longer carrying `needs_recovery` or `orphan_present`.
`e2fsck -fn` on the image passes all five passes.

## 4. The host reboot, unattended

The one thing this project had never observed: a cold host to a running
card with nothing typed. Host rebooted 03:23:18, kernel 7.2.6-1-cachyos,
with `/etc/modprobe.d/phi-vfio.conf` in place.

```
03:23:27.307  systemd-modules-load[399]: Inserted module 'vfio_pci'
03:23:27.338  kernel: vfio_pci: add [8086:225d[ffffffff:ffffffff]] class 0x000000/00000000
03:27:25.898  kernel: vfio-pci 0000:2e:00.0: enabling device (0000 -> 0002)
03:27:26.038  kernel: vfio-pci 0000:2e:00.0: reset done
```

`modules-load.d` inserts the module nine seconds into the boot; the `ids`
option registers the card's id at that moment; `phi.service` opens the
device when the user's session starts.

```
$ readlink /sys/bus/pci/devices/0000:2e:00.0/driver
../../../../bus/pci/drivers/vfio-pci
$ cat /sys/bus/pci/devices/0000:2e:00.0/driver_override
(null)
```

`driver_override` empty is what makes it conclusive rather than suggestive:
`bind-vfio.sh` is the only thing that writes it, sysfs does not carry it
across a reboot, so the binding came from the module option alone. `phi
status` right afterwards reported the unit active, the agent reachable, 228
CPUs, 6143 MiB of swap and `/data` mounted.

## 5. Access surface

Unchanged by design, verified rather than assumed:

```
$ ss -ltnp | grep 2222
LISTEN 0 128 127.0.0.1:2222 0.0.0.0:* users:(("phictl",...))
```

The SSH forwarder binds loopback only. `init` now starts dropbear bound to
the card's own address (`10.9.0.2:22`) rather than every address, which is
the address the forwarder dials; with no `phi0` it does not start dropbear
at all, since there would be no way in. No host TAP device exists, so
nothing off this machine has a route to the card. `loginctl show-user`
reports `Linger=no`, so the unit, and therefore the card, exists only while
the user has a session.

## 6. What was not changed

No `getty`, no `login`, no `crond`, no watchdog. Those are the parts of a
standard install that exist for an unattended multi-user machine; the card
is up only while its owner is logged in, and the two doors (the control
socket and the loopback SSH forward) are deliberate. `/etc/fstab` is written
as documentation and is read by a manual `mount /data`, but `init` does not
use it: the waits for `/dev/phiblk0` and `/dev/phiblk1` to appear have to
happen in an order fstab cannot express.
