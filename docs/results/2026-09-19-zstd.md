# 2026-09-19: zstd 1.5.7 on the card

Follow-on from `2026-09-19-xz.md`. zstd was chosen as the contrast: a much
faster algorithm, entropy-coded with FSE and Huffman rather than a range
coder, and far lighter on memory per thread, so the constraint that capped
xz at 57 threads should not apply.

Same host, same 473 MiB kernel-source corpus, zstd 1.5.7 on both.

## Readings

**zstd is a far worse fit than xz.** The card manages 0.032x the host at
level 1, 0.066x at level 5, 0.061x at level 9, against 0.22 to 0.26x for
xz. The reason is not that the card got worse; it is that zstd is fast, so
the host's advantages compound. At 2.9 GB/s the host is limited by how
quickly it can stream bytes through a small hash table with wide vector
copies, which is exactly what the card cannot do: no SSE for the history
copies, no hardware to hide the per-byte cost, and 228 threads at 1.1 GHz
cannot make up a 30x per-thread deficit on a workload that does very
little work per byte.

The general rule this supports: **the card closes the gap on algorithms
that are expensive per byte and loses badly on algorithms that are cheap
per byte.** xz at `-6` spends hundreds of instructions on each input byte,
which gives 228 slow threads something to chew on; zstd at level 1 spends
a handful, so throughput is set by how fast a core can move bytes, and the
card's cores are slow.

**Thread scaling turns over at two per core, and this time it is
bandwidth.** Level 1 peaked at 114 threads (94 MB/s) and dropped to 78 at
228. That matches the turnover in `card/examples/membw.md` exactly
(80.5 GB/s at 114 threads, 66.0 at 228), and unlike xz it is not a memory
capacity effect: zstd level 1 needs a few MiB per thread, so all 228 fit
comfortably. Levels 5 and 9 are flat from 57 threads upward, which is
consistent with them being compute-bound rather than bandwidth-bound.

So the two compressors fail to scale for opposite reasons, and both
reasons are real:

| | xz `-6` | zstd level 1 |
| --- | --- | --- |
| Best thread count | 57 | 114 |
| What caps it | RAM: ~94 MiB per encoder thread | Bandwidth: two threads per core |
| Symptom past the cap | OOM kill at 228 | Gentle decline to 78 MB/s |

## Levels 3 and 4 fault

```
level 1   OK     20000000 -> 2643118
level 3   FAILED rc=132  Illegal instruction
level 5   OK     20000000 -> 2138137
level 9   OK     20000000 -> 1913379
level 19  OK     20000000 -> 1653412
```

20 `cmov` instructions survive in `zstd_fast.o` and `zstd_double_fast.o`,
which back levels 1 to 4. They are ordinary compiler output for a pointer
select in the hot match loop, not assembly and not a target attribute, and
they should not exist: LLVM patch 0001 makes `canUseCMOV()` false and
patch 0005 adds the branch-expansion pseudo for 64-bit selects. They
survive `-O1`, `-Os`, `-mllvm -x86-cmov-converter=false` and
`-mllvm --disable-early-ifcvt=true`, and they do not reproduce in a
minimal test case, so the trigger needs the register pressure of the real
loop. `card/userland/components/zstd.md` has the detail. This is a gap in
the patched LLVM and wants its own investigation; the audit caught it
before it shipped, which is the point of the audit.

## A second dialect of the same portability bug

xz hid illegal instructions in inline assembly guarded on `__x86_64__`.
zstd hides them in `__attribute__((target("lzcnt,bmi,bmi2")))` applied to
function bodies and dispatched on CPUID at run time. The first build
carried 727 illegal instructions: 660 `shlx`, 27 `lzcnt`, 20 `tzcnt`, 20
`cmov`.

A function-level target attribute **overrides the command line**, so
`-mno-bmi2` never reaches those bodies, and because it resets the feature
baseline instead of adding to it, CMOV returns inside them too.
`-DDYNAMIC_BMI2=0` removes all 707.

Both are the same assumption, that x86-64 implies a feature set, written
two different ways. Anything ported to this card should be checked for
both, and the ISA audit is what finds them: neither is visible in the
build log, and both produce a binary that links cleanly.

## Verdict

Not worth running here, more clearly than xz was. The host is 15 to 30
times faster. The value of the exercise is the contrast: it establishes
that the card's standing against a workload is predicted by how much work
that workload does per byte, and it turned up a real toolchain bug that no
other component had exposed.
