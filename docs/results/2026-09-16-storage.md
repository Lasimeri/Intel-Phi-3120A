# 2026-09-16: persistent storage on the card

The card now has a disk: `/dev/phiblk0`, a 256 GiB sparse ext4 image on
the host's 1 TB NVMe (`/mnt/1TB-NVMe/phi/disk.img`, WD Black SN850X),
served by `phictl boot --disk` over a fourth ring channel and mounted by
`init` on `/data` with `/opt/phi`, `/root` and `/home` bind-mounted from
it. The native toolchain pushed once survives reboots; so does everything
built or written on the card.

## Pieces

- Kernel patch 0025 `knc_blk.c`: blk-mq driver, one record per request,
  512 KiB uncached bounce slots in the channel's data area, a polling
  thread for completions, registration from a workqueue.
- `phictl boot --disk PATH` (`disk.rs`): serves the image, copies through
  the aperture, answers identify with the capacity, `fdatasync` on flush.
- `phi-ring`: channel kind 4, data areas in the region descriptor; the
  default region is 16 MiB.
- `card/initramfs/init`: waits up to 5 s for the device, mounts, binds.
- `scripts/phi-disk.sh` (create, check, usage), `scripts/phi-up.sh --disk`
  and `PHI_DISK`.

## Two bugs found on the way

1. **Host aperture writes are not seen by the card's caches.** The first
   driver handed page-cache pages to the host directly. A test program
   (`aptest.c`, scratch) dirtied a page, had the host write a known
   pattern into it through the aperture, and read it back: 80 of 80 pages
   stale, above and below 4 GiB. The filesystem showed checksum errors and
   neighbouring processes crashed as dirty lines were written back over
   the host's data. The SSDG's "host accesses to coprocessor memory are
   snooped if to cacheable memory" (2.1.12) did not hold for this path.
   Fix: bounce through the uncached ring region, like every other channel.
2. **Torn ring indices from the host.** `ApertureRegion` inherited the
   byte-wise `read_u32`/`write_u32`, so the host published a 4-byte ring
   index as four byte writes and the card could read it half-updated
   (0x00ff to 0x0100 passes through 0x0000). The block driver then
   computed a wrapped byte count and consumed zeros as completions
   ("completion for idle tag 0 status 0" floods, a hung dd). The older
   channels had hidden the same fault behind their resynchronisation
   guards. Fix: single 32-bit accesses (`phi-hw/src/ringmem.rs`), plus the
   same guard in the block driver.

Also fixed: the first version registered the disk from the polling
thread; `add_disk` reads the partition table through the device, which
only that thread could complete, so init hung in `mount`.

## Measurements

Raw device, `dd` with O_DIRECT, 8 MiB per test, checksums equal on both
sides for every size:

| request size | write | read |
| --- | --- | --- |
| 1 MiB | 6.0 MB/s | 9.4 MB/s |
| 64 KiB | 5.1 MB/s | 8.6 MB/s |
| 8 KiB | 4.4 MB/s | 7.8 MB/s |

ext4: a 32 MiB random file written, `sync`, caches dropped, re-read: same
checksum (14 MB/s). After a reboot with `e2fsck -fn` clean in between:
marker file present, toolchain present (26 programs in `/opt/phi/bin`),
a binary built before the reboot runs, `cc` works, SSH works.

Throughput here is bounded by the aperture: the host writes card memory
in paced 4 KiB chunks with a read-back each and reads it with 8-byte
uncached loads, and the card copies through uncached memory. The same
day the DMA engine took over the data path: `2026-09-16-dma.md`.
