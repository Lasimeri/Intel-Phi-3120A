# 2026-09-15: the vector unit, Mandelbrot on the VPU against AVX2

First use of the card's 512-bit vector unit in this port, and the first
time the card beats the host on anything: the Mandelbrot iteration pass at
8K runs in 0.550 s on the card's 228 threads against 0.809 s on the host's
16 threads with AVX2, 26.8 against 18.2 giga-iterations per second. The
x87 build of the same loop took 8.86 s on the card.

## What had to exist first

1. An encoder for the vector ISA. Its instructions carry the MVEX prefix
   (62H, four bytes, ISA reference 327364-001 chapter 3), which no
   assembler or compiler in the stack knows; AVX-512's EVEX differs in
   the prefix (bit 2 of the third byte, 0 for MVEX) and in the payload
   semantics. `host/crates/knc-mvex` encodes full-vector loads and
   stores, `vaddpd`, `vsubpd`, `vmulpd`, `vfmadd213pd`, `vfmadd231pd`,
   `vcmppd`, `kmov` and `kortest`, with unit tests pinning the bytes to
   the macros in Intel's k1om kernel (`mic_ni.h` in the reference tree).
   `knc-mvex-gen` writes the three files that use it.
2. A probe. `card/examples/vpu_probe.c` runs one instruction of each
   kind through `vpu_probe.S` and checks every lane: all seven checks
   passed on the first run, on the unpatched kernel. Nothing enables the
   unit beyond MXCSR.DUE (patch 0018); Intel's tree says the same.
3. Kernel support. FXSAVE does not store the zmm registers and FXRSTOR
   clears bits 0:127 of every one of them (327364-001, B.5 and B.4), so
   without kernel help a task loses its vector registers at every context
   switch. `vpu_state.c` measured it: 128,214 of 623,255 checks
   mismatched with one thread per CPU, 1,231,270 of 1,530,210 with two.
   Patch 0024 keeps 2112 bytes of vector state after the FXSAVE image in
   every task's fpstate, stores it after fxsave and loads it after
   fxrstor (`asm/knc_vpu.h`, generated). With it: 0 mismatches in
   1,168,728 checks (228 threads, 5 s) and 0 in 2,538,356 (456 threads).
   The user ABI (signal frames, ptrace) still carries the FXSAVE image
   only; a signal handler that used the vector unit would clobber the
   interrupted code's registers.
4. The audit tool learned the two encodings: `phi-isa-audit` now sizes
   MVEX instructions itself and counts them as legal, and accepts the
   VEX-encoded mask register instructions that iced-x86 files under
   AVX512F because AVX-512 later reused their encodings.

## The kernel

`card/examples/mandel_vpu.S` (generated) iterates 8 pixels per
instruction: `vcmppd` with its write mask narrows the active lanes,
`kortest` ends the loop when none is left, and under the mask one
`vmulpd` plus one `vfmadd213pd` update the imaginary part, `vsubpd` and
`vaddpd` the real part, two `vmulpd` the squares, one `vaddpd` the count.
The host runs the same sequence as AVX2 intrinsics on 4 lanes
(`mandel-vpu.c`, `-mavx2 -mfma`), so the escape counts are identical on
both machines. The driver times three passes: iterate (the vector part),
colour (the palette through libm, scalar) and the parallel deflate.

## Reading

- The vector unit changes the ratio: on the iteration pass the whole
  card is 1.47 times the whole host (26.8 against 18.2 Giter/s), where
  the scalar builds had it at 0.26 (1.66 against 6.39). Against the
  card's own x87 code the vector loop is 16 times faster.
- Per thread the card is still 5.8 times slower than a Zen 3 thread
  (0.24 against 1.40 Giter/s at 1080p): 4.4 times the clock and one
  in-order issue against two out-of-order FMA ports, partly offset by 8
  lanes against 4.
- SMT is worth 1.88 times here (57 to 228 threads), against 1.52 for x87
  and 1.10 for integer code: a Knights Corner thread cannot issue vector
  instructions in consecutive cycles, so the unit needs at least two
  threads per core to be busy at all, and four to cover latency.
- Lane utilisation is 98 percent: adjacent pixels escape at similar
  counts, so little vector work is wasted at this resolution.
- Peak for comparison: 57 cores x 1.1 GHz x 8 lanes x (one vector
  instruction per cycle) is 502 G lane-operations per second; the loop
  spends 7 vector instructions plus a compare and a mask test per lane
  iteration, so 27.2 G lane-iterations per second is about 50 percent of
  the issue bound. The host's 18.3 G on two 4-wide FMA ports per core at
  about 4.5 GHz is in the same region of its own bound.
- The whole run still favours the host (0.99 against 1.36 s): the
  palette pass is scalar libm on x87 (0.41 s on the card against 0.15 s),
  and deflate is 0.36 against 0.03 s. Vectorising the palette would need
  vector transcendental functions, which the card has as instructions
  (`vexp223ps`, `vlog2ps`, single precision only) and this port does not
  use.
- Images: the card's VPU render and the host's AVX2 render differ in 4
  of 33,177,600 pixels (`magick compare -metric AE`), all from the libm
  palette, since the iteration counts are identical. Against the card's
  x87 render 1,663 pixels differ (extended precision and no FMA there).

## Commands

```
scripts/phi-up.sh --toolchain --ssh                  # boots the kernel with patch 0024
phictl put card/examples/{mandel-vpu.c,mandel_vpu.S} /tmp/
cc -O2 -o mandel-vpu mandel-vpu.c mandel_vpu.S -lz -lpthread        # on the card
./mandel-vpu v8k.png 7680 4320 2000 228
cc -O2 -mavx2 -mfma -o mandel-vpu mandel-vpu.c -lz -lpthread -lm    # on the host
./mandel-vpu v8k.png 7680 4320 2000 16
```
