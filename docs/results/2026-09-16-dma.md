# 2026-09-16: the DMA engine, full PCIe bandwidth for the card's disk

The SBOX DMA engine now moves the block device's data: 3.58 GB/s between
host and card memory in the self-test, raw disk reads of 846 MB/s with
1 MiB requests, against 9 MB/s through the aperture the day before.

## Pieces

- `host/crates/phi-hw/src/dma.rs`: a host-owned DMA channel (channel 0)
  with its 256-descriptor ring pinned in host memory through VFIO, the
  SMPT's first four 16 GiB pages mapped identity so the card reaches IOMMU
  address `x` at `0x80_0000_0000 + x`, memcpy descriptors (40-bit source
  and destination, length in 64-byte lines), completion by polling the
  tail pointer. Register offsets and bit positions from MPSS
  `dma/mic_dma_md.c` and `include/mic/mic_dma_md.h` (reference only) are
  in `phi-regs` (`sbox::DCR`, `dma_reg`, `dma_memcpy_desc`).
- `phictl boot --disk` brings the channel up after init starts, proves it
  with a round trip through the last MiB of the ring region (pattern in by
  DMA, read back through the aperture; pattern in through the aperture,
  read back by DMA), prints the self-test rate, and falls back to aperture
  copies if anything fails (`--no-dma` forces that).
- Kernel patch 0025 gained direct mode: one record per physical segment,
  the request's own pages handed to the host, no copy on the card. The
  host chooses the mode through the tag of its identify answer
  (`0xfffffffe` direct, `0xffffffff` bounce); `knc_blk.direct=0|1`
  overrides.

## Coherence, settled

| host path into card memory | card sees it in its caches | proof (`clevtest.c`, `clevtest2.c`, direct mode forced, raw scratch image) |
| --- | --- | --- |
| PCIe aperture writes and reads | yes, both directions | stamps dirtied on the issuing core and on another core, with and without CLEVICT, all arrived; a host pattern was fresh at once |
| DMA engine reads | yes | dirty lines on the issuing core (W1) and on another core (W2, W3) reached the host |
| DMA engine writes | yes | clean copies on the issuing core (R1) and on another core (R2, R3) were fresh after the copy |

The earlier verdict that aperture writes bypass the caches (`aptest.c`, 80
of 80 stale) was taken on a ring already desynchronised by the torn-index
bug, which completed requests before their data had moved; retracted.
Bounce mode stays as an experiment switch (`PHICTL_DISK_BOUNCE=1`).

## The real corruption: completion before visibility

With direct mode and DMA, metadata-heavy work (the toolchain unpack, a
`cp -r` of it) followed by a hard power-off left the journal unloadable
("Invalid checksum recovering data block") and inodes with bad
checksums, while a 512 MiB block-tagged file written and rewritten in
place verified perfectly on both sides. A host-only stress
(`PHICTL_DMA_STRESS=N`: random lengths and offsets, copy in, copy back,
compare) failed 81 of 3000 and 225 of 10000 copies, every failure
returning the destination's previous contents and the same shapes
failing intermittently on replay: the engine advances its tail pointer
before its writes are visible in memory. Slow large requests never
noticed; rapid small ones read stale data straight after a completion.

Fix, taken from MPSS's DMA library: every submission is one cache line of
four descriptors, the copy, a status descriptor that writes the sequence
number after the copy through the same path, and two NOPs; completion is
the status word (in host memory for copies into host memory, in card
memory read back through the aperture for copies into the card), never
the tail pointer. Padding to whole lines alone did not help (225
failures); the status word did: 0 failures in 10000. A hard power-off
during the churn now replays cleanly (`e2fsck -fp`: 7501 files, no
errors; the tagged file and the toolchain intact). The status polling
costs about 30 percent of the memory-to-memory figure: 2.3 to 2.5 GB/s
in the self-test against 3.6 before.

Also fixed: the two channels' set-up did read-modify-write on the shared
DCR register without a lock, and the ring producer now treats a tail
ahead of its head as a full ring instead of overflowing.

## Measurements

Raw device, `dd` with O_DIRECT, DMA direct mode, 256 MiB per test:

| request size | read |
| --- | --- |
| 1 MiB (two 512 KiB requests each) | 846 MB/s |
| 256 KiB | 370 MB/s |
| 64 KiB | 124 MB/s |

ext4 on the disk: 256 MiB written with `fsync` at 159 MB/s, read back
after a cache drop at 348 MB/s; a 64 MiB random file identical on both
sides (`md5sum` on the card after a cache drop, `debugfs -R cat` on the
host image). DMA memory-to-memory in the self-test: 3.58 GB/s (Gen2 x8).

Bounce mode (aperture, `--no-dma`) after the same driver change: 16 MiB
random file intact, about 14 MB/s. With the engine but bounce slots the
card's uncached copies capped the disk at 14 MB/s too, which is why direct
mode exists.

Where the remaining time goes: one request is served at a time (record,
`pread`, one descriptor, wait, completion), so small requests pay a fixed
latency of about 500 us. Pipelining several descriptors and serving
records in batches would raise the small-request numbers; the 1 MiB
figure is within a factor of four of the link.
