# 2026-09-16: the DMA engine, full PCIe bandwidth for the card's disk

The SBOX DMA engine now moves the block device's data: 3.58 GB/s between
host and card memory in the self-test, raw disk reads of 846 MB/s with
1 MiB requests, against 9 MB/s through the aperture the day before.

## Pieces

- `host/crates/phi-hw/src/dma.rs`: a host-owned DMA channel (channel 0)
  with its 256-descriptor ring pinned in host memory through VFIO, the
  SMPT's first four 16 GiB pages mapped identity so the card reaches IOMMU
  address `x` at `0x80_0000_0000 + x`, memcpy descriptors (40-bit source
  and destination, length in 64-byte lines), completion by polling the
  tail pointer. Register offsets and bit positions from MPSS
  `dma/mic_dma_md.c` and `include/mic/mic_dma_md.h` (reference only) are
  in `phi-regs` (`sbox::DCR`, `dma_reg`, `dma_memcpy_desc`).
- `phictl boot --disk` brings the channel up after init starts, proves it
  with a round trip through the last MiB of the ring region (pattern in by
  DMA, read back through the aperture; pattern in through the aperture,
  read back by DMA), prints the self-test rate, and falls back to aperture
  copies if anything fails (`--no-dma` forces that).
- Kernel patch 0025 gained direct mode: one record per physical segment,
  the request's own pages handed to the host, no copy on the card. The
  host chooses the mode through the tag of its identify answer
  (`0xfffffffe` direct, `0xffffffff` bounce); `knc_blk.direct=0|1`
  overrides.

## Coherence, settled

| host path into card memory | card sees it in its caches | proof |
| --- | --- | --- |
| PCIe aperture writes | no | a page the card had just written kept its old contents, 80 of 80 pages, both zones (`aptest.c`, raw image) |
| DMA engine writes | yes | a page dirtied and immediately read with O_DIRECT received the DMA'd data, 20 of 20 (`aptest2.c`, sector 8) |
| DMA engine reads | yes | a page dirtied and immediately written with O_DIRECT arrived intact on the host (stamp check) |

A false alarm on the way: reading sector 0 kept returning zeros in direct
mode. The mounted ext4 had block 0 cached before the test pattern was
planted from the host and wrote its superblock block back over it; the
host was serving zeros faithfully. Reading a sector the card had just
written itself showed the engine coherent. That stamp test was itself a
mistake: it wrote 4 KiB at sector 8, which on a 4 KiB-block ext4 is
block 1, the start of the group descriptor table, inside a mounted
filesystem. `e2fsck` rebuilt the descriptors from the backups but the
root directory's entries were lost to `lost+found`; the image was
recreated and the toolchain pushed again (a minute). Raw writes belong on
an unformatted image or beyond the filesystem's end.

## Measurements

Raw device, `dd` with O_DIRECT, DMA direct mode, 256 MiB per test:

| request size | read |
| --- | --- |
| 1 MiB (two 512 KiB requests each) | 846 MB/s |
| 256 KiB | 370 MB/s |
| 64 KiB | 124 MB/s |

ext4 on the disk: 256 MiB written with `fsync` at 159 MB/s, read back
after a cache drop at 348 MB/s; a 64 MiB random file identical on both
sides (`md5sum` on the card after a cache drop, `debugfs -R cat` on the
host image). DMA memory-to-memory in the self-test: 3.58 GB/s (Gen2 x8).

Bounce mode (aperture, `--no-dma`) after the same driver change: 16 MiB
random file intact, about 14 MB/s. With the engine but bounce slots the
card's uncached copies capped the disk at 14 MB/s too, which is why direct
mode exists.

Where the remaining time goes: one request is served at a time (record,
`pread`, one descriptor, wait, completion), so small requests pay a fixed
latency of about 500 us. Pipelining several descriptors and serving
records in batches would raise the small-request numbers; the 1 MiB
figure is within a factor of four of the link.
