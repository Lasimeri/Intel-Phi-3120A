# 2026-09-20: upstream FastLanes on the card, with the vector unit under it

`2026-09-20-fastlanes.md` was this project's own implementation of the
FastLanes ideas. This is the other thing: the real library from
`github.com/cwida/FastLanes`, commit `f0edc10`, cross-compiled for Knights
Corner and with its 32-bit decode primitive replaced by MVEX kernels.

Built by `card/userland/components/fastlanes.sh`. Kernels generated by
`knc-mvex-gen fastlanes` into `libknc.a`. Reasoning in
`card/lib/knc-fls/knc-fls.md`.

## The limit, first

Only 32-bit values can go on the vector unit, and that is the hardware.

| FastLanes instantiation | On the VPU | Why |
| --- | --- | --- |
| `unffor` for `uint8_t` | No | Knights Corner has no byte integer vector instruction |
| `unffor` for `uint16_t` | No | and no word integer vector instruction |
| `unffor` for `uint64_t` | No | The whole `Si64` family is `vfixupnanpd`, `vpandnq`, `vpandq`, `vpblendmq`, `vporq`, `vpxorq` (ISA reference 327364-001, appendix D.1.8). No add, no shift |
| `unffor` for `uint32_t` | **Yes** | The `Si32` family has the shifts, the masks and `vpaddd` (appendix D.1.7) |

That is one of four, not three of four. It also matters more than the
count suggests: FastLanes narrows physical types by magnitude, so a column
whose values fit in 16 bits is stored as `u16` and never reaches this
path. On a three-column round trip measured on the host on 2026-09-20,
two columns decoded through `pt=4` and one through `pt=2`. The packaged
example dataset is built to avoid that (`tools/fls-example-csv.md`), and
saying so is part of reading its numbers.

## `unffor` alone, one thread, every width

`/opt/phi/bin/fls_bench`, 1024 values per call, 1024 blocks x 20 reps, so
the input arena is 1.4 MiB at `bw = 11` and well past L2. The scalar
column is FastLanes' own generated code out of the same build, not a
stand-in.

Both vector paths are measured, because the reader takes both. `mvex` is
the kernel on an input at a multiple of four, which it can read directly.
`staged` is the dispatcher on an input one byte off, which it has to copy
into an aligned buffer first, and which is half the calls on a real file.

| bw | scalar M/s | mvex M/s | ratio | staged M/s | ratio |
| --- | --- | --- | --- | --- | --- |
| 0 | 656.8 | 7191.1 | 10.95x | 4538.7 | 6.91x |
| 1 | 125.5 | 1838.7 | **14.65x** | 1301.7 | 10.37x |
| 4 | 132.4 | 1373.4 | 10.37x | 755.1 | 5.70x |
| 5 | 123.3 | 1116.3 | 9.05x | 625.4 | 5.07x |
| 11 | 108.8 | 718.7 | 6.61x | 352.4 | 3.24x |
| 16 | 145.7 | 647.9 | 4.45x | 278.8 | 1.91x |
| 17 | 96.8 | 525.0 | 5.42x | 245.2 | 2.53x |
| 24 | 100.7 | 417.4 | 4.15x | 185.8 | 1.85x |
| 31 | 75.8 | 301.7 | 3.98x | 143.2 | 1.89x |
| 32 | 153.8 | 336.1 | 2.18x | 151.0 | **0.98x** |

The shape is the one bit unpacking already showed
(`2026-09-20-bitunpack.md`): the win is largest where the most values come
out of each loaded word, and it falls towards the bandwidth wall as `bw`
approaches 32, where `unffor` is a copy plus an add and there is nothing
to unpack.

Staging costs roughly half the win, uniformly, and at `bw = 32` it costs
all of it: 0.98x is a wash, because the kernel there is already a copy and
staging makes it two. Special-casing that one width was not worth the
branch, but it is the one place the dispatcher does no good.

The output block is reused, which is not an artificial best case but
exactly the reader's structure: FastLanes decodes into a single
`alignas(64) PT unffored_data[1024]` member and reuses it for every
vector. The input does stream, which is why the arena is sized past L2.

## End to end, which is the number that matters

`/opt/phi/bin/fls_roundtrip` on the packaged example: 60000 rows, three
integer columns, CSV in, `.fls` out, then the file read back a vector at
a time through `RowgroupReader::get_chunk`. That loop is the decode path
with no CSV formatting in it. Timed twice in the same process on the same
file, flipped by a global the shim reads once per 1024 values.

```
encode (csv -> fls)    37.967 s  243493 bytes
decoded              36249600 values in 11800 vectors, best of 3
decode, scalar          0.354 s     102.4 M values/s
decode, mvex            0.197 s     184.1 M values/s
end to end               1.80x
unffor u32, one pass 118 on the vector unit (59 of them staged), 0 fell back, over 59 vectors
```

**1.80x on the whole decode, from 6.6x on the primitive.** The counter
line is what makes that readable. Of the 177 column-vector decodes in a
pass, 118 reach the 32-bit `unffor`, so **two of the three columns, not
three**; the third has 32 distinct values and FastLanes has better
encodings for it than frame of reference plus bit packing.

With that, the whole thing decomposes. 0.354 s over 11800 iterations is
30.0 us per vector-iteration, and each iteration makes two `unffor` calls,
at `bw = 11` and `bw = 17`:

| Part of one scalar iteration | us | share |
| --- | --- | --- |
| `unffor` at `bw = 11`, 108.8 M/s | 9.41 | 31% |
| `unffor` at `bw = 17`, 96.8 M/s | 10.58 | 35% |
| everything else: interpreter, transposes, dispatch, the third column | 10.0 | 33% |
| total | 30.0 | |

So `unffor` is **two thirds** of a FastLanes decode on this card, not a
third. The model predicts the two measured points without adjustment:

| Configuration | predicted us | measured us | ratio |
| --- | --- | --- | --- |
| scalar | 30.0 | 30.0 | 1.00x |
| one column direct, one still scalar | 22.0 | 22.2 | 1.35x |
| one column direct, one staged | 15.6 | 16.7 | **1.80x** |
| both direct (not reachable: the data is not aligned) | 13.4 | | 2.24x |

Three things separate 6.6x from 1.80x, in order of size: one column in
three never calls `unffor` at all; one of the two that do is staged, which
is 2.5x rather than 6.6x; and the remaining third of the pipeline is
untouched. Only the second is something this port could still improve.

## Staging the unaligned inputs, worth 1.35x to 1.80x

The first version fell back to scalar whenever the input was not 4-byte
aligned, since `vloadunpackld` is `#GP` below element granularity. The
counters said that was **59 of 118 calls**, half the work, so half the
available win was being given away to satisfy an alignment the data
simply does not have.

The fix is to copy the packed bytes into an aligned scratch buffer and run
the kernel on that. It looks expensive and is not: the copy is of the
*compressed* data, at most 4096 bytes and usually far fewer. The staged
column in the table above prices it: about half the direct win, so 3.24x
instead of 6.61x at `bw = 11`, against 1.00x for giving up. End to end it
moved 1.35x to 1.80x and the fallback count to zero.

This is the same shape as the earlier finding that `valignd` cannot be
used here: the misalignment is a run-time value, `valignd` takes an
immediate, and generating sixteen variants per width is not worth it. A
`memcpy` is.

## Correctness

`/opt/phi/bin/fls_check`, on the card:

```
fls_check: 0 of 1381 comparisons failed
```

Four sweeps: every bit width 0 to 32 at every 4-byte input offset 0 to
60, twice each (the kernel directly, and through the patched
dispatcher); every byte offset 0 to 63 at five widths, which is the
staging path; the four base-pointer offsets; and one output pointer that
is not 64-byte aligned, which must fall back rather than fault.

The reference is not a model written for the test. It is FastLanes' own
generated `unffor`, called under the name the patch renamed it to, in the
same process on the same bytes. A misreading of the layout on my part
could not pass it.

## The bug the first version of that check did not find

The first version of the check had no base-pointer offsets and passed.
The first real decode took a general protection fault, at
`ip 0x14915ed`, which `llvm-nm` puts at the first instruction of
`knc_fls_unffor_b11`: `vpbroadcastd zmm26, [rdx]`.

The dispatcher guarded the alignment of `in` and `out` and passed `base`
straight through. A FastLanes base segment holds four bytes per vector
but starts at an arbitrary byte offset in the file, so `a_base_p` is
routinely not 4-byte aligned. `*(a_base_p)` in the scalar code it
replaces is a legal misaligned load and never noticed; `vpbroadcastd` is
`#GP` on such an address (ISA reference 327364-001, VPBROADCASTD,
"Exceptions").

The fix is a `memcpy` into a local, one load and one store per 1024
values. The four new base offsets in `fls_check` cover it: with the fix
reverted, the program exits 139 there rather than reporting a failure,
which is what a `#GP` looks like from userspace. Verified both ways on
the card.

The general lesson is the one already on record from the input pointer:
**on this card every pointer that reaches a vector instruction is a
separate alignment contract, and scalar code that worked proves nothing
about any of them.** The input was caught by reading FastLanes' allocator
before writing the kernel. The base was not, because a single scalar
broadcast did not look like a pointer at all.

## Three encodings that had to be verified on hardware first

`vpbroadcastd`, `vloadunpackld` and `vloadunpackhd` are new to the
encoder, and MVEX is dense enough that a wrong prefix bit decodes as a
different valid instruction rather than faulting. `card/examples/vpu_int.c`
covers them: slots 16 and 17, plus a sweep of the unaligned load pair at
every 4-byte offset from 0 to 64. All pass; the bytes are pinned in
`integer_bytes_verified_on_the_card`.

The unaligned pair is not an optimisation, it is a requirement.
`SegmentView::PointTo` sets `data = data_span.data() + get_offset(...)`,
and those offsets accumulate entry-point arrays that can be one byte per
vector, so a bitpacked segment starts at an arbitrary multiple of four
inside the file buffer. Measured with a probe inside `Unffor` on
2026-09-20, the residues modulo 64 were 8, 48 and 60. `vmovaps` faults on
all three. That check cost an hour and would have cost a day as a fault
inside a 182 MB library.

## Four patches to upstream

Two are portability, one is a real bug, one is the port itself.

| # | File | Change |
| --- | --- | --- |
| 1 | `src/include/fls/cuda/common.hpp` | `#include <climits>`; `CHAR_BIT` reaches that file only transitively on the compilers upstream builds with. Needed for the host build too |
| 2 | `src/table/stats.cpp` | `last_seen_val(0)` to `last_seen_val {}`; the template is also instantiated for `std::string`, where `string(0)` is `string(nullptr)` |
| 3 | `src/alp/src/fastlanes_gen_unffor.cpp` | Rename the `uint32_t` dispatcher to `unffor_scalar`, one line |
| 4 | same file, appended | The new `unffor`, which checks two preconditions and calls `knc_fls_unffor` |

Patch 2 is worth reporting upstream on its own; it is undefined behaviour
on any compiler, not a Knights Corner problem.

`-Wno-pass-failed` is not a patch. It lives in `toolchain/cmake/knc.cmake`
because no loop on this card can be vectorised by the compiler at all:
LLVM has no Knights Corner backend, so every `#pragma clang loop
vectorize` fails its transformation and `-Werror` makes that fatal.
FastLanes' own CMakeLists already carves out the same exception for CI
runners without AVX-512. That diagnostic is also the clearest possible
statement of why `libknc` exists.

## Audit

`libFastLanes.a` for the card is 3.6 million instructions and audits
`0 illegal, 0 suspect, 0 KNC vector`: nothing the compiler emitted is
outside what the card implements, and no vector instruction is in there
at all, which is exactly right, because the compiler cannot emit one.
Every vector instruction in the final binaries comes from `libknc.a`.
